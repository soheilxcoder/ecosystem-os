# 11 — Module: Notifications

## Purpose
Every time-boxed rule in this platform (90-day cycles, 3-day voting windows, 30-day correction periods, 90-day entry trials) only functions as "automatic" if people are actually told when a window opens or closes. This module is the delivery mechanism for every reminder referenced across Modules 2–10.

## User stories
- As any user, I want a single place to see everything that needs my action.
- As a Pod Lead, I want to be reminded before the pitch window opens and again before it closes.
- As a Peer Validator, I want to be told the moment I'm assigned a review, with a due date.
- As a Coach, I want to be flagged when an assigned pod's health turns red.

## Screen: `/notifications`
- **Two tabs**: "Needs Action" (unread + action-required items) and "All Activity" (full log, read-only, includes already-actioned items).
- Each notification row: icon (matching source module), title, one-line context, timestamp, primary action button if applicable (e.g., "Review pitch" → deep-links directly into `/review/queue` pre-filtered to that item).
- **Bulk "Mark all as read"** for the All Activity tab only (Needs Action items can only be cleared by completing the underlying action, not by dismissing the notification — this prevents someone from "clearing" a pitch-review reminder without actually reviewing it).
- **Notification bell** in the top nav (Module 1's sidebar) shows an unread-count badge, split visually by urgency (red dot = action required with a deadline within 48h, gray = informational).

## Delivery channels
- **In-app** (always, this screen + bell badge) — the system of record.
- **Email** (configurable per user, default ON for "Action required" and "Urgent action," default OFF for "Informational" digest-only).
- **Digest email** (daily or weekly, user-configurable) — rolls up "Informational" items so users aren't spammed for every single event.
- No push/SMS in v1 (flagged as a v2+ item in the roadmap if mobile app usage patterns justify it).

## Screen: `/settings` → Notification Preferences
- Per-trigger-category toggle (Action required / Urgent / Informational) × per-channel (In-app / Email / Digest) matrix — simple checkbox grid.
- "Urgent action required" items cannot be fully muted (a minimum in-app delivery is enforced) — only their email channel is user-configurable — since these map to hard deadlines with real consequences (e.g., pitch auto-submit).

## Data model
```
Notification
  id, recipient_user_id, trigger_type, urgency (informational|action_required|urgent),
  title, context_text, deep_link, related_entity_type, related_entity_id,
  read_at (nullable), actioned_at (nullable), created_at

NotificationPreference
  id, user_id, urgency_level, channel (in_app|email|digest), enabled (bool)
```

## Business logic
- Notifications are generated by the same event-emission mechanism described in Module 10 (Archive) — a single internal event bus that both the Archive indexer and the Notification dispatcher subscribe to, so every meaningful state change produces both a historical record and a real-time alert from one source of truth, rather than two separately maintained trigger lists that can drift apart.
- "Action required" notifications remain in the Needs Action tab until the underlying action is actually completed (checked by querying the related entity's state, not by a separate "dismissed" flag) — this guarantees the Needs Action list is always truthful.

## API endpoints
- `GET /api/notifications?tab=action|all`
- `POST /api/notifications/:id/read`
- `GET /api/notifications/preferences`
- `PUT /api/notifications/preferences`
